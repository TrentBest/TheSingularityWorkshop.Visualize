# SVG living documentation

**Purpose:** make Visualize's real contracts visible inline. Each picture below names the code path that produces it and says exactly what the picture proves—and what it does not.

> **Reading rule:** an SVG can be a generated, inspectable manifestation of real inputs without being a GPU render. These are engineering proof surfaces, not a claim that the production graphics pipeline is complete.

## Start here: the frame-to-SVG handoff

![Generated GUI.SVG connected-points proof](../samples/PrimitiveGallery/generated/07-gui-svg-connected-points.svg)

**What you're seeing:** four differently colored point meshes, segment meshes connecting them, and an irregular closed trail. The checked-in SVG is generated by `integrations/GuiSvg/Proof/Program.cs`: it builds real Visualizer geometry, material resources, draw commands, and a `VisualizerFrame`; the optional `GuiSvgVisualizerBackend` consumes the frame and GUI.SVG serializes the neutral scene.

**What it proves:** the public Visualizer frame/resource contract can be consumed by the optional GUI.SVG integration and turned into an SVG artifact.

**What it does not prove:** the animated markers are SVG presentation, not an FSM simulation; the proof uses a simple XY mapping, not perspective-correct, depth-tested 3D or GPU-produced pixels.

## More advanced proof outputs: generated by CI

The following proofs are generated by the C# integration path in CI and are downloadable from the run's named artifacts. Open the run, scroll to **Artifacts**, and download the corresponding ZIP.

- [Open the latest documented proof run](https://github.com/TrentBest/TheSingularityWorkshop.Visualize/actions/runs/39369513107)
  - **`visualize-city-massing-proof`** — three material skins and a JSON report for the Renderer → `RenderFrame` → `RendererFrameAdapter` → Visualizer → GUI.SVG path.
  - **`visualize-svg-primitive-proof`** — generated primitive, perspective-mesh, and GUI.SVG feature-gallery proof outputs.
  - **`visualize-extremus-crowd-proof`** — deterministic crowd/instance SVG and manifest.
  - **`gui-svg-feature-gallery`** — generated GUI.SVG features such as gradients, clipping, patterns, markers, symbols, animation, filter graphs, and lighting definitions.

**City massing: what it proves.** The fixture creates a real Renderer `RenderFrame`, adapts its ordered commands into a Visualizer frame, and emits three material skins. Its executable assertion verifies that command count/order and each command's geometry/material IDs, world transform, index range, representation, and entity ID survive the adapter. The report's `adapterCommandOrderAndIdentityPreserved` field is set only after the check succeeds. The distant representation omits selected window-detail face commands: this is command-level work reduction, not GPU buffer compaction or a production city renderer.

**Perspective mesh: what it proves.** The proof submits an indexed octahedron through Visualizer's geometry, material, draw-command, and frame contracts, then applies CPU world/view/projection transforms and painter ordering. It does not provide GPU depth testing, general clipping, or production lighting.

**Crowd/instance proof: what it proves.** It makes the fixture's deterministic instance data visible in a generated artifact. It does not establish the performance of a GPU crowd renderer.

The named artifact contents are snapshots from the cited workflow run. If the branch has advanced, rerun CI or use the run linked above to inspect exactly the output produced by that run.

## Run the proofs yourself

From the Visualize repository root:

```bash
dotnet run --project samples/PrimitiveGallery/VisualizeSvgProof/VisualizeSvgProof.csproj --configuration Release
dotnet run --project integrations/GuiSvg/Proof/GuiSvgProof.csproj --configuration Release
dotnet run --project integrations/GuiSvg/CityMassingProof/CityMassingProof.csproj --configuration Release
```

The optional GUI.SVG integration uses the GUI repository's source project in development CI. Visualize core must not require GUI.SVG.

## Evidence rules

- Generated SVGs must come from the C# contract path they claim to show; don't redraw output in HTML/JavaScript and call it backend output.
- Keep source input, rendered result, and measurable assertions linked from the documentation.
- Identify CPU projection, SVG manifestation, and GPU execution separately.
- Keep SVG animation explicitly presentational unless a real data/control loop drives it.
- Preserve inspectable artifacts in the repository or CI, and regenerate/compare deterministic snapshots.
- For GPU claims, require an actual selected backend, device/surface creation, submitted work, verified GPU-produced pixels, and exercised resize/shutdown paths.

## Cross-repository boundary

Renderer decides which representation and draw commands are appropriate; Visualize consumes presentation contracts and resources; GUI.SVG serializes a neutral GUI scene to SVG. Renderer remains independent of both downstream packages. The [Renderer SVG guide](https://github.com/TrentBest/TheSingularityWorkshop.Renderer/blob/work/svg-living-docs/docs/SVG_LIVING_DOCUMENTATION.md) documents the Renderer-owned state snapshot and executable `RenderFrame` inspector.
